# .lad 字节结构速查

排错用。写程序不需要读这一份——工具会处理。但文件被别的软件改坏、或者要判断"生成得对不对"时，这些不变量能定位问题。

## 1. 整体

- **无文件头**。没有 magic number、没有版本号字段、**没有校验和**。
- 主体是 **40 字节一个记录**，每个记录 = **10 格 × 4 字节**。
- 文件尾是 `00 fe` 两个字节。
- 长度检查：`len % 40 == 2` 且最后两字节是 `00 fe`。

没有校验和这件事要记住：**改错一个字节，编辑器不会报错**，只会显示一张不对的图，或者把某个元件接到别的地址上。

## 2. 一格（4 字节）

```
[b0]      连接位 conn
[b1]      元件 opcode
[b2]      地址低字节
[b3]      地址高字节
```

位元件地址是 16 位：`addr = b2 | (b3 << 8)`，编码为 `(设备索引 << 9) | 编号`。

| 设备 | 索引 | 例 |
|---|---|---|
| I | 0 | `I100` → 0x0064 |
| O | 1 | `O200` → 0x02C8 |
| C | 2 | `C36` → 0x0424 |
| S | 3 | |
| A | 4 | `A302` → 0x092E |

编号超过 511 会被 `& 0x1FF` 截断 —— 工具现在会直接报错而不是生成错的文件。

常见单格 opcode：空 `0x00`、横线 `0x0d`、常开触点 `0x01`、常闭触点 `0x03`、
定时器触点 `0x09/0x0a`、计数器触点 `0x0b/0x0c`、
线圈 `0x0e`(NO)/`0x10`(NC)/`0x05`(RP)/`0x07`(FP)/`0x12`(LATCH)/`0x14`(UNLATCH)。

## 3. 连接位 conn（b0）

| 位 | 含义 |
|---|---|
| bit0 | **右边界**上半段有竖线 |
| bit1 | **右边界**下半段有竖线 |
| bit2 | **左边界**上半段有竖线 |
| bit3 | **左边界**下半段有竖线 |

相邻两格必须镜像，这是编辑器 AutoFix 的判据：

```
左格.bit0 == 右格.bit2      (上半段)
左格.bit1 == 右格.bit3      (下半段)
```

不满足 → 编辑器打开时会提示自动修正（或图上有断口）。

一条竖线在列边界 B 上跨第 r0..r1 行时：r0 只置下半段、中间行上下半段都置、r1 只置上半段。

## 4. 8 字节块（功能块）

定时器、计数器、运算、比较、END 占 **2 格 = 8 字节**：

```
[b0 b1 b2 b3] [b4 b5 b6 b7]
 conn op idx  0    lo hi lo 80
```

- 后 4 字节整个都是参数区，**第二格没有 conn**，它那 4 个字节位被参数占用。
- 参数是 16 位小端，低字节重复一次：
  - 定时器 preset 60（1s）→ `3c 00 3c 80`
  - 定时器 preset 300（0.1s）→ `2c 01 2c 80`
  - 计数器 preset 50 → `32 00 00 80`（注意这里**没有**重复低字节，与定时器不同）

**`+7` 那个字节是保留位，不是校验位，也不是参数尾标记。**
编辑器生成的样本里常见 `0x80`，但真机文件里也有 `0x00`——`cnc.lad` 的定时器参数是
`0a 00 0a 00`，`END` 的第二格多数文件是 `00 00 00 00`。
所以：**不要用"末字节是不是 0x80"来判断某格是不是参数区**，只认 opcode。

## 5. END / FEND 是双格，只有 RTS 是单格

这是本项目踩过的最深的坑。官方 `plcop_map` 把整个 Flow 组都标成双格（`bi=1`），
但**序列化时有一个例外**：

```
END  行:  00 cf 00 00 | 00 00 00 00 | 00 0d 00 00 ...   → END 占 8 字节
FEND 行:  00 fd 00 00 | 00 00 00 00 | 00 0d 00 00 ...   → FEND 占 8 字节
RTS  行:  00 d0 00 00 | 00 0d 00 00 ...                 → RTS 占 4 字节（唯一例外）
```

END / FEND 的第二格是保留区，编辑器写全零（14 个文件）、个别真机文件是 `00 00 00 80`（`cnc.lad`）。
**两种都能正常打开**，判据只有一个：**第二格绝不能是横线 `00 0d 00 00`**。

出现横线就说明它被当成 4 字节写了，那一行后面整体错位一格——这是最隐蔽的一类错，
因为 END/FEND 通常在行尾或段尾，错位之后没有任何元件受影响，格式检查也照样通过。

反过来，把 `RTS` 按 8 字节读，会吞掉后面正常跟着的横线格，同样整行右移。
所以判据是：`RTS(0xd0)` 单格；`END(0xcf)` / `FEND(0xfd)` 双格；其余 8 字节块都要吃下一格。

## 6. 非逻辑行：注释 / 版本

**判据**：`b1 == 0` 且 `b3 != 0`（正常逻辑格里 b1 是 opcode，不可能为 0）。

此时：
- `b2` = 本段落占用的**字节数**（不是字符数）
- `b3` = 注释类型 ct

| ct | 含义 | 占编辑器行号 |
|---|---|---|
| 1 | 整行注释 | ✅ 占 |
| 3 | 整行注释（另一种排版用） | ✅ 占 |
| 2 | 版本行 | ❌ 不占 |
| 4 | 设备变量注释（挂在地址上） | ❌ 不占 |

**编辑器行号 = 逻辑行数 + ct∈{1,3} 的注释行数**。给用户报行号时必须按这个算，
不能直接用内部段序号——加了 5 条程序头注释，梯形图整体后移 5 行。

### 注释里可能混着非 cp950 字节

真机文件（`cnc.lad` 2 条、`cnc_1.lad` 1 条）里存在**不是合法 cp950 的注释**，
例如 `93 7c`——这段按 GBK 能解成「搢」，按 Big5 直接抛异常。

成因是早年有人在 Big5 字段里用 GBK 输入法打了字，编辑器不做校验就存下去了。
**这不影响程序运行**，只是在编辑器里显示成乱码。

所以：`check_lad.py` 对这类只报 `[WARN]`，不报 `[FAIL]`。
如果你自己新写的程序出现这条警告，那才是真问题（多半是没转繁体），要回去改。

## 7. 排错流程

```bash
python scripts/check_lad.py 程序.lad -v
```

它会依次检查：长度 `40N+2`、尾部 `00 fe`、每记录 10 格、8 字节块是否吃掉下一格
（以及是否落在最后一格导致没地方放参数区）、相邻格 conn 镜像、末行是否 END/FEND/RTS、
END 第二格是不是横线、注释块能否按 cp950 解码。

**它不检查参数区末字节是不是 `0x80`**——见 §4，那个字节不可靠，真机里 `0x00` 也合法。

按报错类型判断原因：

| 现象 | 多半是 |
|---|---|
| 长度不是 40N+2 | 文件被截断，或某处多写/少写了 4 字节 |
| 末行不是 END/FEND/RTS | 缺少结束指令。注意带子程序的文件末尾是 `RTS`（`cnc_1.lad` 就是），多程序段是 `FEND`，都合法 |
| END 的第二格是 `00 0d 00 00` | END 按 4 字节写了，整行错位一格 |
| conn 镜像不匹配 | 生成时竖线范围算错，编辑器会提示 AutoFix |
| 注释解出来是乱码 | 写注释时没有转 cp950 繁体 |
| 图整体右移一格 | 某处 8 字节块被当成 4 字节（少吞了一格） |
| 图整体左移一格 | 某处 4 字节单元被当成 8 字节（多吞了横线） |

## 8. 什么改了会坏，什么改了没事

- **安全**：在末尾加一段、改某个线圈地址、加/改注释。
- **要小心**：插入或删除中间的一段（后面的行会整体移动；注释是按"前面有几条逻辑行"定位的，
  工具会跟着调整，但手工改文件不会）。
- **危险**：手工编辑字节。没有校验和，错了不报错。
- **不可能做到**：让重新生成的文件和人工排版的版本逐字节相同。编辑器的列位和留白是人工摆放的，
  没有规则可循（全量语料里几何逐字节一致率 778/1188，剩下的差在留白）。
  结构一致（树相同）才是正确目标。
